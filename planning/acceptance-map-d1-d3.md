## How to read the matrix

`Planned` means tests/implementation are specified for the installed variant, not that the full canonical scenario has passed. The last column explicitly identifies variants requiring later deliverables. `Intentionally not advertised` means the capability is absent in D1–D3; prerequisite facts may already be retained. A row with a narrow early variant does not certify its later variants.

The unit/structural column links the complete named per-case TDD specification and its exact unit selectors. The flow column links the real-stack integration fixture and Given/When/Then plus independent production-browser critic checklist. Execute each flow using the exact selector procedure in the shared guide, for example `npm run test:acceptance -- --project=chromium --grep D2-A07`; shared titles include scope, such as `D2 B-11`. Provider rows additionally require the actual live-provider command; performance rows require the benchmark command. These scripts will be established by D1-T01 and are not runnable planning evidence.

Every planned row inherits the shared authoritative before/after manifest, exact accepted response/restart comparison, no-write/rollback proof, evidence provenance and fresh-critic gate. Its linked flows add scenario-specific fixtures and outcomes. All applicable shared safety checks repeat for every new installed mutation/fact family. Future scenario-specific task/test IDs will be assigned while detailing the complete D4–D20 plan rather than invented here.
