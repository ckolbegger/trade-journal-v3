# thinkorswim (Charles Schwab) as a Mark provider

Research task 4 of 4, written 2026-11-15. It judges Schwab's APIs and the thinkorswim desktop app against `research/mark-provider-requirements.md` (R1 to R41, Q1 to Q12) for D11 (`plan/implementation-plan.md`, D11 section).

How this was researched: documentation only. Nothing was registered, no one logged in, and no Schwab service was called, so the CORS checks in R26 and R30 were not run. Schwab's developer portal (developer.schwab.com) needs a login and refuses automated reads (HTTP 403), so most API facts come from well-kept community projects that quote it: schwab-py (active on 2026-11-15), Schwabdev (updated 2026-11-13), community TypeScript types copied from Schwab's OpenAPI file, and forum posts. The thinkorswim Learning Center (toslc.thinkorswim.com) is public and is cited directly.

Evidence labels: **Documented** = an official Schwab or thinkorswim page. **Community (date)** = a third-party project, forum or blog, with its date. **Inferred** = my reasoning from the evidence, not yet checked.

## 1. Verdict

**Plain answer.** Schwab does offer automatic prices, but not in the form this app needs.

- **Stocks and ETFs: yes, with a catch.** The Schwab Market Data API returns daily open, high, low and closing prices for any date range, going back decades. But community sources say the history is split-adjusted, with no switch to turn that off. So a backfill across a split gives the wrong Mark (R17).
- **Options: only today's bid and ask, never history.** The user has settled Q1: an option's Mark is the closing bid/ask midpoint. Schwab's live quotes do carry each contract's bid, ask and its own `mark` field (that midpoint, rounded to the cent), so the session that just ended can be valued. But **no Schwab endpoint returns past end-of-day bid and ask for options**: price history is stocks only, option chains start at today, and there are no prices for expired contracts. If the trader skips a few days, turns the provider on for an older position, or holds a contract past expiration, those option Marks can never be fetched. They stay Manual tasks (fails R14 and R15 for options; R6 only partly met).
- **It cannot run from the static web page alone.** The login uses OAuth with a client secret, which a browser page cannot keep secret. No source shows a browser-friendly (PKCE-only) login. No source shows that Schwab's servers allow calls from a web page (CORS), and the only JavaScript library says browser use is "a poor choice". On top of that, the login expires every 7 days and must be redone by hand, with no way to extend it.
- **thinkorswim desktop on a Mac cannot be the server.** thinkorswim has no local API on macOS. Its Excel link (RTD) is Windows-only, thinkScript cannot write files or talk to other programs, and its history tools (charts, thinkBack, OnDemand) can only be read on screen. The only way to get data out is a manual "Export to file…" of the Position Statement or a watchlist: today's values, by hand, as a CSV file.

**Which architecture is workable?**

| Architecture | Workable? | Why |
|---|---|---|
| A. Browser only (the app calls Schwab directly) | **No** | Needs the client secret in the browser; CORS unknown and probably absent; fails R30 and R31. |
| B. thinkorswim desktop as a local server on macOS | **No** | No local interface on macOS exists (Documented for RTD; Community for the rest). |
| C. A small local bridge on the Mac (for example a schwab-py script on 127.0.0.1) | **Technically yes, but outside the spec** | It works the same way as D. The spec forbids "a locally running gateway" (R30). The trader must keep it running and log in again every week. |
| D. A small cloud proxy (Cloudflare Worker or Pages Function) that holds the secret and refresh token | **Technically yes, but outside the spec** | The cleanest of the four. It is still new server infrastructure (decision 15 says to stop and discuss). It puts a brokerage token in the cloud, and it needs a weekly login. |

Even C or D only fixes the access problem. The data gaps stay: no option history, no expired contracts, and split-adjusted stock history. **Recommendation (Inferred):** do not choose Schwab as the D11 provider. Keep Marketdata.app as decision 13 says. Schwab could become a second adapter later, only if the user accepts a proxy, a weekly login and "options only on the evening of the session" coverage. The model allows one enabled provider at a time (`specs/design/market-data.md:153`), so Schwab cannot just fill the gaps of another provider.

**Why the user may think thinkorswim supports this.** thinkorswim desktop does show all of this data: option charts, a decade of daily option chains in thinkBack, and Schwab's `Mark` column (the bid/ask midpoint). It just does not let any other program read it on a Mac (Inferred from the sections below).

**Option symbol format (Community).** Schwab uses the padded OCC form: the root padded with spaces to 6 characters, then YYMMDD, `C` or `P`, then the strike × 1000 as 8 digits, for example `AAPL  240517P00190000` ([Schwabdev troubleshooting](https://github.com/tylerebowers/Schwabdev/blob/main/docs/pages-raw/troubleshooting.md); schwab-py `OptionSymbol.build()` uses `'{:<6}{}{}{:08d}'`). The app's key is the same thing without the padding, so the mapping is a pure rule (R3). Indexes take a `$` prefix (`$SPX`). Inside thinkorswim desktop, options use a different form (`.AAPL240517P190`), which only matters for manual exports.

**History: TD Ameritrade to Schwab (Community).** Schwab bought TD Ameritrade. The TD Ameritrade API stopped working after the market closed on 2024-05-10 ([schwab-py tda-transition](https://schwab-py.readthedocs.io/en/latest/tda-transition.html): "As of May 13th, 2024, the underlying API that powered tda-api is no longer working"). Old apps and tokens were not carried over. The replacement is the **Schwab Trader API – Individual** (or Commercial). An app adds the API products "Accounts and Trading Production" and "Market Data Production". Changes in the move: app approval is no longer instant, `localhost` is no longer a valid callback, refresh tokens went from 90 days (renewable) to 7 days (not renewable), the option symbol format changed, and the watchlist and saved-order endpoints were dropped.

**Open questions this provider helps answer.**

- **Q1 (settled by the user: the closing bid/ask midpoint).** What Schwab offers for that rule:
  - **Schwab's `mark`, defined precisely.** thinkorswim's own pages disagree. The glossary says "Mark is the midpoint between the bid and the ask" ([Glossary M](https://toslc.thinkorswim.com/center/Glossary/M), Documented). The scan-filter page says "For futures, single options, and stock, mark price is the last price bounded by bid and ask. For other securities, it is the arithmetic mean of bid and ask" ([Scan Filters](https://toslc.thinkorswim.com/center/howToTos/thinkManual/Scan/Filters), Documented). The API's option data follows the **midpoint** rule, rounded to the cent. In the community chain sample (AAPL options expiring 2024-10-18, quote time 16:00:00 New York time), the 15-strike call had bid 218.80, ask 221.90 and last 204.80, and `mark` was 220.35. That is the midpoint; "last bounded by bid and ask" would give 218.80. Contracts that never traded had a `mark` too (bid 224.00, ask 226.35, `mark` 225.18) (Community: [Schwabdev chains example](https://github.com/tylerebowers/Schwabdev/blob/main/docs/pages-raw/api.md); Inferred). For stocks, the samples' `mark` was neither the midpoint nor clearly the last price, so it should not be used for stocks.
  - **When.** A quote read after the session ends holds the closing bid and ask, stamped with `quoteTime` (`quoteTimeInLong`). Use that time to check it belongs to date D (R7, R35).
  - **`closePrice` for options.** In the same sample, the never-traded 10-strike call had `closePrice` 222.16, and the 5-strike call's `closePrice` was 227.16 while its last trade was 225.88, four days earlier. So an option's `closePrice` is not a last trade. It looks like the previous session's closing midpoint (Inferred). For stocks, `closePrice` in the evening is the previous session's value: AAPL at 19:58 on 2024-10-18 showed `closePrice` 232.15 (the 2024-10-17 value) and `regularMarketLastPrice` 235.00.
  - **History.** None. No endpoint returns any past session's bid and ask for options (R6).
  - **Consequence for R11.** A midpoint Mark and a Bar's closing (last-trade) price will differ. With Schwab, option Bars would exist only on the session's own evening anyway (R10).
- **Q9 (16:15 options).** Not documented. A quote read after 16:15 reflects 16:15 trading.
- **Q10 (index options).** `$SPX` levels and SPXW contracts exist, with the same no-history limit.
- **Q12 (minimum credential scope).** Schwab cannot issue a data-only credential. The best case is an app limited to the Market Data product (Inferred, unverified), still issued through a full brokerage login.

## 4. thinkorswim desktop as a local server

**Plain answer: not possible on macOS.** thinkorswim desktop has no interface that another program, a browser page or a local bridge can read on a Mac. Every way data leaves it either runs on Windows only or needs a person to click.

The only real path is semi-manual: each evening, export the Position Statement to CSV and import it into the app. That is a separate import feature, not a Pricing Provider adapter (decision 14's port fetches by Instrument key and date). It would also give only Schwab's `Mark` (midpoint) at the moment of export, and nothing for skipped days.

**Friction, security, cost and fit for B:** not applicable, since it does not work. The semi-manual CSV route needs no install beyond thinkorswim, costs nothing, adds a daily click-export-import step, and fits neither the adapter boundary nor "the app fetches by itself" (story 1).

## 5. The server or proxy options

Both C and D talk to the same Schwab API, so they share the data limits in section 3: stocks with history (split-adjusted), options for the current session only.

### C. A small local bridge on the Mac

**What it is.** A small program (for example 50–100 lines of Python using schwab-py) runs on the Mac. It does the OAuth login with the callback `https://127.0.0.1:8182`, keeps the token file, and serves a tiny HTTP endpoint on 127.0.0.1 that sends CORS headers for the app's origin. The adapter calls that endpoint instead of Schwab.

| Aspect | Assessment |
|---|---|
| Feasibility | High. This is exactly how schwab-py and Schwabdev are meant to be used: "users who want to run applications on their own machines" (Community: schwab-py auth docs). |
| What the user installs or runs | Python 3.10 or later (Python 3.11 certificates on macOS for Schwabdev), the bridge script, and a login item or `launchd` job to keep it running. A self-signed certificate for the callback server, which the browser warns about at each login. |
| Daily or weekly friction | Daily: none, if the bridge is running when Daily Review opens. Otherwise recovery fails safely and the trader types Marks. Weekly: a full Schwab login (with two-factor) in the browser before the 7 days run out. Schwab's own projects advise doing it every Sunday. |
| Security | The secret and refresh token stay on the Mac, in a file outside the browser and outside backups (good for R33). Any local program that can reach 127.0.0.1 could ask the bridge for data, and possibly place trades if the app has the trading product. Limit the app to Market Data Production (Inferred) and bind to 127.0.0.1 only. Only one refresh token is valid at a time across machines (Community: Schwabdev troubleshooting). |
| Cost | Free. |
| Fit with decision 14 and the credential rules | The adapter would be a normal HTTP adapter, but against the bridge. Credential fields in the app would shrink to "bridge address", because the real credentials live in the bridge. It breaks R30 ("no … locally running gateway") and moves part of the provider code out of the one adapter folder into a separate program the app cannot test with its conformance suite alone. |

### D. A small cloud proxy (Cloudflare Worker or Pages Function)

**What it is.** A Pages Function on the same origin as the app (for example `/api/schwab/*`), or a separate Worker, keeps the app key and secret as Worker secrets and the refresh token in Workers KV or a Durable Object. The trader clicks "Connect Schwab". The page sends them to Schwab's login, Schwab redirects to `https://<app>.pages.dev/api/schwab/callback`, and the Function swaps the code for tokens. After that, the adapter calls the Function, which refreshes the access token every 30 minutes and forwards `quotes` and `pricehistory` calls. On the same origin there is no CORS question at all.

A lighter variant: the Function only does the token exchange and refresh, and hands the 30-minute access token to the browser, which calls Schwab directly. This works only if Schwab's market-data endpoints allow CORS (Unknown).

| Aspect | Assessment |
|---|---|
| Feasibility | High technically (Inferred). Schwab accepts any HTTPS callback URL that matches the registered one exactly; `127.0.0.1` is only the common choice (Community: schwab-py getting started, "Advanced users may be able to use a non-local callback URL"). Changing the callback URL means re-approval, "which typically takes a few days" (Community). |
| What the user installs or runs | Nothing on the Mac. The project gains a Function or Worker, KV or a Durable Object, and two Worker secrets. That is new server code, deployment and tests, outside the current "static app, no server" stack (`plan/technology-stack.md`). |
| Daily or weekly friction | Daily: none. Weekly: a full Schwab login through the app's "Reconnect" button before day 7. A missed week means Marks are not fetched until the trader logs in. Automating the login (for example with Puppeteer, [schwab-api-auth-automation](https://github.com/digitalml/schwab-api-auth-automation)) would mean storing the brokerage password and two-factor secret in the cloud. Do not do this. |
| Security | The serious cost. A refresh token for a real brokerage account lives on a server reachable from the internet. Anyone who can call the Function, or read KV, can read account data and, unless the app is limited to Market Data, place trades. The Function needs its own authentication (for example Cloudflare Access in front of it, or a per-device secret), which is yet another credential. Mitigations: Market Data product only (Inferred); Cloudflare Access; revoke on disconnect through `/v1/oauth/revoke` (Community: schwab-py #267). |
| Cost | Inferred from Cloudflare's published plans (not re-checked here): the free Workers plan (100,000 requests a day) and the free KV tier easily cover a few dozen calls a day. A Durable Object or the paid Workers plan costs about US$5 a month. |
| Terms | The API agreement is behind the login (Unknown). Schwab's model for Individual apps is personal use by the account holder; a personal proxy used only by that holder is in that spirit. A proxy shared by several people would be the Commercial product (Inferred). |
| Fit with decision 14 and the credential rules | The adapter fits the port cleanly, since it is just HTTP to the Function. But the credential leaves the device: the spec keeps the credential "device-local … outside every backup section" (D11 mechanisms; `specs/design/market-data.md:153`). Here the real secret is in the cloud, and the app holds only a session with the proxy. Restore would bring the configuration back as Needs Setup, and the proxy's token would still be valid. Decision 15 says to stop and discuss before any proxy. |

## 6. Registration, costs and terms

**Registration (Community: schwab-py getting started, Schwabdev setup guide, TradersPost 2026-09-16).**

1. Have a Schwab retail self-directed brokerage account. Enable thinkorswim on it (log in to thinkorswim once).
2. Create a developer account at developer.schwab.com with the **same email** as the brokerage account.
3. Request access to the product "Trader API – Individual". This is reviewed.
4. Create an app: choose the API products ("Market Data Production"; add "Accounts and Trading Production" only if needed), an order limit, a name and description, and one or more HTTPS callback URLs (comma-separated). `localhost` is refused, `https://127.0.0.1[:port]` works, and there must be no trailing slash.
5. Wait for the status to go from "Approved - Pending" to "Ready For Use", "a few days" in reports. Problems go to traderapi@schwab.com. Callback validation bugs were reported on the developer site in July 2024.
6. Copy the App Key and Secret, then do the first login (Schwab login, accept terms, choose accounts) to get the first refresh token.

**Lead time (Community):** a few days to more than a week. **Restrictions (Community):** no sandbox for Individual apps. A new refresh token from one machine invalidates the old one. Order-related limits (4,000 order calls a day) do not matter here.

**Costs.** The API and its market data are free to Schwab account holders (Community; no pricing exists). Real-time quotes need the non-professional exchange agreements signed in the account; otherwise quotes are delayed (Community: schwab-py docs: "If your account limited to delayed quotes, these quotes will also be delayed"). Delayed quotes would hardly matter for evening Marks. No OPRA fee was found for non-professionals. A cloud proxy adds about US$0–5 a month (Inferred).

**Terms.** The API terms of use and any market-data redistribution clauses are behind the developer login and were not read (Unknown). Schwab's public site terms give a "limited personal license" (Documented, general terms). Storing end-of-day prices on the device and in one's own backups for a personal journal is probably within personal use, but this must be confirmed in the developer portal's terms before relying on it.

## 7. Risks and open questions

**Risks.**

1. **No option history, and no historical bid/ask (decisive).** With the Mark defined as the closing bid/ask midpoint, Schwab can supply it only from a live quote, so only on the evening of the session (or, Inferred, through `closePrice` the next day). Any day the trader does not open Daily Review on the session's evening (or perhaps the next day) leaves option Marks Manual forever. That includes enabling the provider for existing positions, expired legs of open spreads, and Settlement Due Trades (R15). This undercuts story 1 for an options trader.
2. **Split-adjusted stock history (R17).** A backfill or re-fetch across a split returns rewritten prices. That would append misleading refresh revisions, or seed wrong Marks on empty keys.
3. **Weekly manual login.** It is enforced by Schwab and cannot be extended ("There is currently no way to make a refresh token last longer than seven days"; Schwab's API team said it "might change in the future, but no set timeline": [schwabr](https://cran.csiro.au/web/packages/schwabr/refman/schwabr.html), Community, undated). Missed logins look like silent provider failures.
4. **Brokerage credential exposure (R32, Q11, Q12).** There is no data-only key. Whatever holds the token holds a key to the trader's brokerage account.
5. **New infrastructure.** Every workable Schwab architecture adds a server or local gateway that the spec rules out (R30, decision 15).
6. **Undocumented behaviour.** Closing-price timing, `closePrice` roll-over, provisional values and class-share spelling are all undocumented. Schwab has changed behaviour and invalidated tokens without notice (Community).
7. **Zero used as "missing" in option quotes (R8).** The adapter must not turn 0 OHLC into a Bar.
