Making the Review page look and work like the cockpit

The Review page still looks like the app did before the Trade Detail cockpit: one long column of plain text, with every Mark asked for in a tall stacked list. This page recommends rebuilding it in the cockpit's style. A rail on the left holds the Review's status and the selected Trade. Drawers on the right hold Marks, Reflections and Action. Marks for several sessions go into one compact grid, styled like the cockpit's Price History.

These recommendations are written to feed the prototype that the D08P plan asks for before any build. The user signs off each screen visually, then a breakdown follows. The prioritised list is at the end.

In short
  1. The layout: a cockpit-like Review. The rail holds the Review's status (a "Needs you" list in the spec's work order) and the selected Trade's cards. The main column holds the Trade list, then drawers for Marks, Reflections, Settlement (only when due) and Action.
  2. One Marks grid per Trade, styled like Price History. It shows the Review Date and the previous session always, then each earlier session without Marks, 20 at a time.
  3. Prices typed but not yet saved (drafts) belong to the Review, not to one card. A price typed for a shared Instrument shows as filled, not as an input, in every other Trade that holds it. Save Marks saves every draft at once.
  4. A cell editor under the grid holds "Can't get a price", Correct and Withdraw, each with its reason. The cells stay small, and A57 still applies: Withdraw is offered on the Review Date only.
  5. On a phone, sessions become rows and Instruments become columns, so nothing scrolls sideways for a single-leg Trade.
  6. One data addition: the Review's open also returns the Marks it doesn't carry today, for the previous session and for mixed gap sessions. They come from the read session's series, which shares the existing gaps scan. That adds no new operation and no schema change, but the Review's interface does change.
  7. Three small fixes come first: the "<date> close" heading, acknowledged sessions in Price History, and Price History's gain and loss colours.

2. The Review today

The Review was built in D5R from its own prototype, before the cockpit existed. It works: one card per Trade in attention order, panels for Marks, Reflections and Action, and Save Marks saving a card's drafts together. But it reads as a long plain document, and the Marks panel grows by about 200 px for every missing session of every Instrument.

  1. 1Status is plain text. The cockpit uses a "Needs you" card, with small-caps labels and hairlines between items (ReviewView.tsx:153-177 compared with rail-b.css:66-90).
  2. 2The same reason is repeated on every figure, seven times on this card. The cockpit says it once on the P&L card and uses the short label "Mark missing" elsewhere (CardFigures.tsx:17-35).
  3. 3Conditions are a bulleted sentence list. The cockpit draws one block per condition, with a red or green role, a figure on the right and a muted line saying why (CardFigures.tsx:40-61 compared with rail-b.css:1-64).
  4. 4"Mon Oct 5 close" breaks the Mark wording rule. Trade Detail already says "At the Mon Oct 5 Marks" (W19); the Review card was missed (CardFigures.tsx:108).
  5. 5Every missing session is a full block: date, "Missing", a full-width input, a hint and a pill. They are grouped by Instrument, so the two prices of one session sit far apart (CardMarks.tsx:186-238).

3. The cockpit-like Review

The Review keeps its job and its rules: Trades in attention order, each with Marks, Reflections, Settlement when due, and an Action, with nothing saved until the trader presses Save. What changes is the frame. It becomes the cockpit's frame: a rail that always shows where the Review stands and which Trade is open, and drawers for the work on that Trade.

4. The Marks grid

The Marks drawer holds one grid for the selected Trade. Each row is one of the Trade's Instruments (the stock, or a contract and its Underlying). Each column is a session, newest on the left, as in Price History. It always shows two sessions, then any session missing a Mark.

  • The Review Date, which the user called "Today". Its Marks are needed to complete the Review.
  • The previous session, which the user called "yesterday". It is shown even when its Marks exist, so the trader sees what they are comparing with.
  • Each earlier session missing a Mark for any of the Trade's Instruments, newest first, 20 per page. They are optional, as today.
Why not the words "Today" and "Yesterday": a Review is often done the next morning, and Monday's previous session is Friday. The date headers ("Thu / Oct 8", as W9 has them) carry the meaning. A small tag names the role: "Review Date", an existing term, and "Previous", which is new and needs approval.

Keyboard. Enter moves down the current session's column first (all of one session's Instruments), then to the next session, and from the last input to Save Marks. That matches how a trader copies one statement day at a time, and matches the phone's row order (section 7). Today Enter follows DOM order (CardMarks.tsx:341-344). Trade P&L row. I recommend leaving it out of the Review's grid. If the user wants it, getTrade would add a dated evaluation for the previous session through its existing dated-line path (decision 102's "one read per distinct earlier date").

5. Shared Instruments and drafts

A Mark belongs to an Instrument and a session, not to a Trade. If two Trades hold XYZ, they share one XYZ Mark for Thu Oct 8. The user asked that a price typed in one card fill the same cell in every other card, which then stops showing an input. To do that, drafts move from the card to the Review page, keyed by Instrument and session. The Trade where the price was typed owns the input. Every other Trade shows the value.

1 · Typed in the first Trade

XYZ, Long 100 @ $50.10
51.80
XYZ, Long 50 @ $50.00
51.80Unsaved · typed in XYZ (Long 100 shares @ $50.10)

The second Trade shows a filled chip, not an input. The chip is a button: pressing it moves the input to this Trade, and the first Trade then shows the chip. The rail counts one unsaved Mark, not two.

2 · Saved

XYZ, Long 100
51.80
XYZ, Long 50
51.80

Save Marks, pressed in either Trade or in the rail, saves every draft on the page in one SaveReviewMarks. Both cells become plain saved Marks, from the result's standings, as the held Review does today (held-review.ts, the fold).

3 · Cleared before saving

XYZ, Long 100
XYZ, Long 50

Emptying the owner's input removes the draft, and both Trades show inputs again. Discard, in either place, empties every draft on the page.

4 · Corrected after saving

XYZ, Long 100
51.85Corrected
XYZ, Long 50
51.85Corrected

Correct saves at once with its reason through MarketData.save, as today, and every Trade shows the new value with "Corrected". A Conflict ("This Mark changed after you opened it…") is shown in the cell editor of the Trade where it was attempted.

What this changes in the code. Drafts move from CardMarks's state (CardMarks.tsx:262) to the screen. The screen already keeps each key's standing in the held Review (held-review.ts, A171-A172), and the drafts would sit beside it. SaveReviewMarks already accepts any of the Review's keys (A155) and 1 to 100 entries, so saving drafts typed in several Trades needs no backend change. With more than 100 drafts, Save Marks says so before sending; this needs a new sentence.
Paging gets simpler. Paging is blocked today while a draft exists, because changing page would unmount the inputs (CardMarks.tsx:189-207). With drafts held by the page, paging can go on and the drafts stay.

A price fits in a cell. "Can't get a price" and Correct each need a reason, which doesn't fit. Withdraw and the "also held by" list need room too. Three ways to give them room:

Why B. It keeps today's rules exactly:
  • "Can't get a price" is a draft with a required reason (A153).
  • Correct and Withdraw save at once, one key at a time (D5R table, "Correct and Withdraw stay one row at a time").
  • A57 offers Withdraw only on the Review Date.
  • The settlement-only note ("Needed only while settlement is due") and "also held by" stay.
It also gives one fixed place for Conflict and storage-failure messages, which today sit inside each row's region. The editor is a region named after the cell ("Call Mark, Tue Oct 6"), so links into the Review (?instrument=, A161) can focus it.

7. The grid on a phone

At 390 px wide, a grid with a pinned label column fits two or three session columns. Two ways to handle more:

When it turns. By the drawer's width, not the device: a container query, as the Review card's slider already uses (app.css:949-956). Below about 40rem the table turns, and both layouts use the same cells. If D10 brings Trades with three or four legs, the turned table scrolls sideways like any other wide table (.table-scroll). It's still one table with the same accessible names, so narrow and wide screens offer the same actions (ui-contract, "Responsive behavior").

8. What data the grid needs

The Review already holds most of what the grid shows. It lacks Marks that exist for sessions other than the Review Date. The grid needs those for the previous session, and for any shown session where one Instrument has a Mark and another doesn't (Mon Oct 5 above).

Column or cellHeld today?Where from
Review Date: every stateYesThe Marks family's Review-date rows (MarkRow: resolution with price, revision, task and the Trades holding it).
Earlier sessions: Missing and Acknowledged UnavailableYesThe gap groups: dates, revisions and acknowledgments, trimmed to each Trade from the date it is relevant (held-review.ts:79-90).

The smallest addition. When open builds the Marks family, Daily Review also reads each Instrument's series from the read session, from the earliest shown session to the Review Date. It returns, per Instrument, the Available Marks for the previous session and for the listed gap dates: price, revision, source and correction reason.
  • Where the data comes from. series already exists (D08P, A210, market-data.ts:306) and shares the session's one gaps scan per Instrument (decision 106). So it should add no stored read. A query-count proof, like D08P's I8P.4, must confirm that before the work is agreed.
  • Interface change The Daily Review open result gains an additive field in the Marks family. Save results already return the saved keys, so the fold needs only to handle the new field.
  • What doesn't change: no Market Data operation, no schema, no fixture.
  • Performance: AC-PERF-001's Review-open row and tech debt item 3 (the open grows with history) must be re-measured, since this touches the open path.
Rejected alternatives.
  • Read replayTrade per selected Trade: a second coordinator on the screen, bound to a Trade Detail binding rather than the Review's, and a full replay per Trade switch. It would fit only if the Trade P&L row is wanted for every column.
  • A point frame per extra date: one more read per distinct date, which grows with the number of gap columns.

  • Cells are 44 px high on touch screens.
  • Colour never carries meaning alone: words or accessible names carry every state.
  • Focus is visible. After a refused save, focus goes to the first issue in the cell editor.
  • The tabs follow the WAI-ARIA pattern. Narrow and wide screens offer the same actions, and resizing keeps drafts.
  • Contrast meets WCAG AA. The new blue draft chip (--info-ink on --info-ground) needs checking, and forced-colours mode needs borders.
