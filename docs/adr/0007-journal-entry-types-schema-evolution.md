# Trader-configurable Entry Types with tolerated schema drift

Every Journal Entry has an Entry Type that defines the Prompts it asks. Both the set of types and each type's Prompts are trader-configurable, seeded with rich defaults. When a type's Prompts change, existing entries are never migrated — each entry permanently keeps the Prompts and answers it was written against, and historical analysis must tolerate entries of the same type having different shapes.

Tolerating drift is not the same as tolerating loss. A select Prompt's options carry a stable `id` alongside their display `label`, and an answer stores the **id**. Renaming an option is therefore a display change, and every answer given under the old wording still resolves; without this, a rename would silently orphan every prior answer, since the answer would *be* the old string. This is the one identity guarantee the drift model depends on — anything that edits a Prompt must preserve option ids across a rename rather than rebuild the list.

Rejected: a fixed journal schema (the trader's reflection practice evolves faster than the app ships), and migrating old entries on schema change (rewrites history — the answers were given to the old questions, not the new ones). Also rejected: versioning Entry Types, whether as a separate field or by making the id a composite like `trade-review_2`. Each entry already snapshots the prompts it was asked, so a version number adds no information the record lacks; and putting the version in the id fragments the stable `entryTypeId` that makes "every Trade Review entry, ever" a single query — defeating the purpose it would be introduced to serve.
