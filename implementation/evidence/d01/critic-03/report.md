## Finding C03-01 — fixed narrow navigation clips an installed action under supplemental 200% rendering

**Implementation rendering defect; B05 fails.** This is an observation about the exact CSS rendering condition below, not a claim of verified native browser-chrome zoom.

Reproduction on the base production build:

1. Open native WebKit with a 390×1000 viewport and complete ordinary onboarding.
2. Open New Plan and enter values. The recorded reproduction first exercised a stale Catalog save and native Plan-stage abort, then Retry startup; those faults were removed and the ordinary form remained.
3. In the browser document, apply `document.documentElement.style.zoom = '2'` only as a supplemental rendering stress condition. No app code, viewport size, quota or authoritative data changes.
4. Inspect the fixed bottom navigation. Trades and New Plan are visible, while **Workspace extends past/clips at the right edge**. Document `scrollWidth === clientWidth === 390`, so a document-overflow check alone misses the clipped action.

Expected: all installed primary navigation actions stay visible, readable and operable across the supported narrow/reflow presentation. Actual: Workspace is clipped. Screenshot: **`supplemental-css200-390.png`**; exact script/method and raw measurement: `critic03-final-ui-script.txt`, `final-ui-transcript.txt`, `final-ui-results.json`. The 1440 supplemental rendering did not show this clipping.

Relevant passages: `specs/design/ui-contract.md:35`: “Every supported width exposes equivalent information, fields, actions, validation, and Save/Cancel outcomes.” `specs/design/ui-contract.md:125` requires “readable zoom/reflow” and “equivalent narrow/wide actions.” D1-T08 and B05 explicitly include 200% reflow. A regression should inspect **each installed nav action's full visible bounds**, not only document scroll width. Root acknowledged this as an observed rendering defect and will perform the required test-first repair/new-critic loop. This critic made no fix.
