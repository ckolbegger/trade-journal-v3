# Acceptance matrix

Part of the [implementation plan](implementation-plan.md), as required by the planning protocol's Phase 4. It has one row for every scenario in the [acceptance contract](../specs/acceptance/acceptance-contract.md), 67 in all.

## How to read it

**Rolling-wave planning (decision 40).** D1–D8 have task-level breakdowns, so their rows name tasks, TDD case groups, integration cases, critic flows, commands, and expected evidence. Each deliverable's own section 8 holds the full text, and this matrix links to it. D9–D28 are planned at the deliverable level. When a later deliverable is broken down, an approved plan revision fills in the cells for that deliverable and keeps this matrix in step with its section 8.

**Full in** is the deliverable where the scenario becomes full, from the plan's [acceptance coverage index](implementation-plan.md#acceptance-coverage-index). "D28 (cumulative)" marks a cumulative obligation that every deliverable re-proves for what it adds.

**Status values:**
- `planned`: every clause is planned at task level in D1–D8.
- `planned: task level in D1–D8; deliverable level from D9`: D1–D8 plan the clauses they claim, and later deliverables complete the rest, as the **Later** note says.
- `planned at deliverable level`: no D1–D8 task covers the scenario yet. Its required evidence is copied from the acceptance contract.
- `covered`: used once implementation evidence exists.
- `intentionally not advertised`: no scenario has this status.

**Kinds** are the categories the protocol requires the matrix to distinguish:
- **C**: pure calculation examples.
- **M**: module contract tests.
- **T**: multi-module transaction and evidence-race tests.
- **U**: browser, responsive, and accessibility behavior.
- **P**: PWA identity, browser-tab operation, production HTTPS and secure-loopback evidence, browser-neutral readiness, and engine/OS provenance.
- **L**: repeated launch, runtime failure, `Recovery Only`, restart, offline, update, migration, and Restore.
- **B**: verified, unverified, and failed-verification backups, and exact-target `CompletedBackupReceipt` enforcement.
- **S**: deterministic target-scale correctness and percentile benchmarks.

## Evidence methods common to every row

- **No-write and rollback claims** compare full dumps of every store in `tj-root` and every Workspace database before and after, including the root's `pointer` and `candidates` records and the list of databases. Node cases use `fake-indexeddb`; browser cases use the read-only IndexedDB probe after a reload or a full browser restart. A Restore rollback also checks that the pointer still names the old database and that no candidate database remains after a restart (D8 section 8).
- **Secrets exclusion** is checked by D8's I8.3. It scans every decompressed line of a real backup for excluded stores, private fields, and secret-shaped keys, and checks the manifest's exclusions. From D11, a credential canary saved through `configureProvider` must be absent from the backup (decisions 37 and 38).
- **Restart and durability** use a restart in Node (a new application on the same factory), and a reload, full browser restart, offline cold restart, or SIGKILL after commit in the browser.
- **Engines and provenance.** Routine browser evidence runs in Chromium with the faults build (decision 19). Firefox, WebKit, and real-state readiness evidence for the AC-DEL rows is pending RC. Production HTTPS evidence for AC-DEL-003 is pending the Cloudflare project (decision 4). Every run records exact engine and OS versions as provenance, never as an allowlist. The versions frozen with the plan are in the [technology stack](technology-stack.md#pinned-versions).
- **Red/green and structural evidence** go to `evidence/D<nn>/tdd-log.md` and `structural.md`, and critic reports to `critic-<n>.md` (section 10 of each breakdown).
